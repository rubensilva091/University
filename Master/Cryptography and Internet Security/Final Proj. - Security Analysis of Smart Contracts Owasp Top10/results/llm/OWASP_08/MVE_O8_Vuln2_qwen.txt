### Vulnerability 1: **Reentrancy (Cross-function)**  
1. **Vulnerability Type**: Reentrancy  
2. **Severity**: Critical  
3. **Affected Functions**:  
   - `withdraw()` (lines 10–17)  
   - `transfer()` (lines 19–23)  
4. **Description**:  
   The `withdraw()` function performs an external call (`msg.sender.call{value: amount}("")`) **before** updating the user's balance. During this call, an attacker-controlled contract could re-enter the `transfer()` function, which uses the stale (pre-withdrawal) balance to allow an invalid transfer. This enables draining funds by exploiting the race condition between the two functions.  
5. **Recommended Fix**:  
   Follow the **checks-effects-interactions** pattern: update the user's balance **before** making the external call in `withdraw()`. Additionally, consider adding a reentrancy guard (e.g., `ReentrancyGuard` from OpenZeppelin) to prevent reentrancy entirely.

### Vulnerability 2: **Lack of Reentrancy Guard**  
1. **Vulnerability Type**: Reentrancy  
2. **Severity**: High  
3. **Affected Function**: `transfer()` (lines 19–23)  
4. **Description**:  
   The `transfer()` function does not include any reentrancy guards or checks to prevent recursive calls. If an attacker triggers a reentrant call to `transfer()` during the external call in `withdraw()`, they can exploit the stale balance to perform unauthorized transfers.  
5. **Recommended Fix**:  
   Add a reentrancy guard (e.g., `nonReentrant` modifier from OpenZeppelin) to both `withdraw()` and `transfer()` functions to prevent recursive calls.

**Most Critical Finding**: Cross-function reentrancy between `withdraw()` and `transfer()` allows attackers to drain funds by exploiting stale balances during reentrant calls.

### Summary of Fixes:  
- Update `withdraw()` to update balances **before** external calls.  
- Add reentrancy guards to both `withdraw()` and `transfer()`.  
- Consider using `sendValue()` or `transfer()` instead of `call{}` for safer ETH transfers.
