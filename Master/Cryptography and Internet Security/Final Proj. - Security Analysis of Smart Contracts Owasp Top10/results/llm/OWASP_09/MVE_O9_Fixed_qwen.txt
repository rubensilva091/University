### Security Audit Report

---

#### **1. Vulnerability: Missing Access Control**  
- **Severity**: Critical  
- **Affected Function**: `mint(uint256 amount)` (lines 14–21)  
- **Description**: The `mint` function is publicly accessible and allows any address to mint tokens up to the `MAX_SUPPLY`. This violates the principle of least privilege and enables unauthorized inflation of the token supply.  
- **Recommended Fix**: Restrict `mint` to a specific role (e.g., contract owner) using an `onlyOwner` modifier or a role-based access control mechanism like OpenZeppelin’s `AccessControl`.

---

#### **2. Vulnerability: No Anti-Whale Mechanism**  
- **Severity**: Medium  
- **Affected Function**: `mint(uint256 amount)` (lines 14–21)  
- **Description**: While the contract enforces a `MAX_SUPPLY`, it allows a single address to mint the entire supply in one transaction (e.g., `mint(1_000_000 ether)`). This creates a centralization risk if a single entity controls the initial mint.  
- **Recommended Fix**: Add a per-transaction or per-address minting limit (e.g., `require(amount <= MAX_MINT_PER_TX, "exceeds limit")`).

---

#### **3. Vulnerability: No Event Emission for Minting**  
- **Severity**: Low  
- **Affected Function**: `mint(uint256 amount)` (lines 14–21)  
- **Description**: The contract does not emit an event when tokens are minted, making it difficult for external systems to track supply changes.  
- **Recommended Fix**: Add an event like `event Minted(address indexed minter, uint256 amount)` and emit it after minting.

---

### **Overall Security Score**: **4/10**  
**Most Critical Finding**: Missing access control allows unrestricted minting of the entire token supply, rendering the "cap" ineffective and enabling inflation attacks.
