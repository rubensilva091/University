### Identified Vulnerabilities

1.  **Vulnerability Type:** Logic Error / Unfair Bonus Distribution
    *   **Severity:** Medium
    *   **Affected function and line number(s):** `claimBonus`, lines 16-18
    *   **Brief description of the risk:** The `bonusClaimed` mapping is tied to the `msg.sender` address, meaning a user can only claim the 0.1 Ether bonus once, ever. This contradicts the inline comment `// [FIX] Regra corrigida: bonus so pode ser reclamado uma vez por deposito.` which implies that a bonus should be claimable once *per eligible deposit*. As implemented, if a user deposits 1 Ether, claims the bonus, then deposits another 1 Ether (total 2 Ether), they cannot claim a second bonus. This leads to an unfair bonus system and potential user dissatisfaction.
    *   **Recommended fix:** Re-evaluate the bonus claiming logic. If the intent is indeed "once per eligible deposit," adjust the state variable and logic to track eligibility for multiple claims (e.g., by associating claimed bonuses with deposit thresholds or a cumulative amount). If the intent is "one bonus per address, ever," update the comment for clarity.

2.  **Vulnerability Type:** Denial of Service (DoS) / Funds Stuck
    *   **Severity:** Medium
    *   **Affected function and line number(s):** `withdrawAll`, lines 27-29
    *   **Brief description of the risk:** If the `msg.sender` address is a smart contract that is not designed to receive Ether (e.g., lacks a `receive()` or `fallback()` function, or its functions explicitly revert), the `msg.sender.call{value: amount}("")` operation will fail. This will cause the entire `withdrawAll` transaction to revert, preventing the user from withdrawing their legitimate funds.
    *   **Recommended fix:** To prevent funds from being permanently stuck, consider providing an alternative withdrawal mechanism, such as allowing users to specify a different withdrawal address or implementing an `emergencyWithdraw` function callable by the contract owner to recover stuck funds (though the latter should be used cautiously). Alternatively, clearly document the requirement for `msg.sender` to be able to receive Ether.
